# 资料面板与待发送消息 · 设计原型

状态：**Experiment / TBD**，2026-11-03。不是产品合同，不改 `docs/ui-ux.md`。

两套待发送（pending steer）方案共用同一套资料面板重画，便于单独比较滚动区与输入区的差别。

## 打开

```sh
cd apps/zenx/prototypes/information-steer
python3 -m http.server 41785 --bind 127.0.0.1
```

打开 `http://127.0.0.1:41785/prototype.html`。底部原型条可切换：

- **A · 消息流内** / **B · 输入区上方**
- **等待进入** / **已进入模型**（看状态切换时消息是否跳动）
- **深色** / **浅色**

「全部撤回」会真的把两条消息合回输入框并弹出提示；自动化开关、问题选项、数字键 1/2 都可操作。
截图参数：`?v=a|b&theme=dark|light&state=pending|entered&chrome=0`。

## 资料面板：改了什么

1. **问题卡**
   - 原生 radio → 整行按钮：15px 选择圈、选中填 accent、行高 ≥44px、数字键 1–9 可选中。
   - 选项描述独立成行（12.5px/11.5px），不再和标题挤在一行。
   - 自由回答始终可见，输入框 `resize: none` 并自动增高；无 resize 手柄、无滚动条。
   - 明确的两个出口：「取消请求」文字按钮 + 「发送回答」主按钮；左侧写明「发送前不会提交任何内容」。
2. **自动化**
   - `Enabled / Paused` 文字 → 真开关（30×18，44px 命中区）。开为 accent 轨道，关为中性轨道 + 白色 knob。
   - 暂停行整行降级（标题、图标变 muted），但保留名称和触发条件，便于重新打开。
   - 副行给出可判断的信息：间隔 + 下次时间 / 信号名 / 来源线程；不再堆段落。
   - 计数写成「2 启用」，而不是无解释的 `2 / 3`。
3. **子会话 lineage**
   - 扁平列表 → 状态点 + 标题 + 相对时间 + 一行活动摘要；固定行高，活动更新不跳行。
   - 子级用左侧细导轨缩进；进行中的点带 3px 光晕，空闲为中性点。
   - 「新建旁聊」收进 section header 的 `+`，不再占一行。
4. **终端**：一行 `command` + 运行状态与时长，等宽字体。
5. **节奏**：section 之间只用 1px 分隔线，不做卡片套卡片；标签 11px/0.06em，正文 12.5–13.5px，保持 340px 栏宽内可读。

## 待发送消息：两套方案

### A · 消息流内（`captures/focus-a-pending-dark.png`）

气泡与普通用户消息完全相同，只在批次下面多一行：`⟳ 2 条等待进入模型 · 下一步执行时一并提交 | ↩ 全部撤回`。进入模型后这行消失，气泡不动。

- 好处：所见即所得；claim 时零跳动；与 `PendingSendRows` 的既有语言一致；语义上它确实是一条已被 Host 接纳的消息，不是草稿。
- 代价：未进入上下文的內容暂时出现在会话记录里，撤回后气泡会消失；待发送多时会给消息流增加高度；撤回入口离气泡稍远。
- 细节：状态行始终可见（不做 hover-only），撤回是带文字的 24px 胶囊，命中区用伪元素扩到 44px；批次只有一个撤回入口，符合原子撤回。

### B · 输入区上方（`captures/focus-b-pending-dark.png`）

右对齐的小块：标题「待发送 2」+「全部撤回」，内部是同样的消息气泡，底部一行等待状态。小块随内容收缩（最小 440px，最宽到输入区宽度），进入模型后整块消失、消息出现在消息流同一位置。

- 好处：未进入上下文的东西不混进会话记录；撤回与输入区在一起，操作距离短；多条时可限制高度滚动，不挤压阅读区。
- 代价：多一块界面，占用输入区上方的垂直空间；claim 时会发生「从块里跳到消息流里」的位置跳变；气泡在块里几乎是满宽，气泡感会被容器削弱。

### 对比

| | A 消息流内 | B 输入区上方 |
| --- | --- | --- |
| 消息身份 | 就是消息，只是未 claim | 明确的「待发送」暂存 |
| 进入模型时 | 位置、样式都不变 | 从块里消失，出现在消息流 |
| 撤回距离 | 批次下方一行 | 与输入区同一块 |
| 多条堆积 | 拉长消息流 | 块内滚动 / 折叠 |
| 与现有实现的连续性 | 延续本地发送气泡 | 延续现有 pending 区域 |
| 主要风险 | 未 claim 内容提前进入「历史」 | 多一层表面 + 位置跳变 |

**建议：A。** 理由不是它更漂亮，而是它把「已经交给 Host、但还没被下一次模型输入 claim」这件事表达成消息的等待状态，而不是草稿；claim 后不需要任何视觉迁移。B 更适合「一次攒很多条、反复调整」的用法，可以作为 A 在多条时的折叠形态，而不是另一套主界面。

若选 A，实现时补两点：批次超过 3 条时把中间折叠成「还有 N 条」；撤回成功后气泡与状态行一起 150ms 淡出，同时输入框获得焦点并合入正文。
