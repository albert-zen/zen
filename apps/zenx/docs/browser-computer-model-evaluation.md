# Native ZenX model trials, 2026-09-19

These exploratory trials ran real `gpt-5.6-luna` and `gpt-5.6-sol` agents inside a newly built ZenX portable application on Windows. They used the normal subscription provider, App Server, plugin discovery, installed bundled packages and hosted tool execution. An external protocol client submitted prompts and recorded results; it did not choose controls or perform the tasks. This is distinct from deterministic provider smoke tests and from a Codex model driving a diagnostic transport.

The evaluated application was built from `1c45a96958e740a4307853037015d3958b7af73f`, with Browser 1.0.2, the default packaged Playwright provider, Computer 1.1.1 and WinApp CLI 0.3.1. Both models used the configured Medium reasoning default. Each independent task started a fresh thread; desktop missing-window recovery continued the preceding desktop thread. The application used isolated data and disposable fixtures. Model prompts contained task instructions and tool-use constraints, not fixture source or evaluator success conditions.

Keep these as blocked concurrency evidence, not model failures or successful trials. The final runner uses an empty evaluation workspace; this earlier run does not validate that corrected workspace boundary.

## Concrete improvements identified

1. **Give a conflicting caller a usable recovery path.** All hosted capability tools currently share the `external:zenx-capability-host` bundle resource. Different browser sessions and even Computer discovery can therefore conflict with another thread's browser operation. The busy error says to use `wait`, but supplies no caller-owned task ID; waiting on another thread's task is correctly forbidden. The traces include repeated retries and `Tool task not found for this thread`. Narrowing resource ownership and yielding a caller-owned queued operation would address this without weakening thread isolation. This remains follow-up work.
2. **Reduce model round trips for ordinary forms.** Even the successful serial two-field form required four inspections and nine waits. Both models explicitly reported asynchronous waiting as friction. A bounded form-filling operation, cheaper observations and measured tuning of the yield interval are useful candidates; these trials do not isolate their individual latency contributions.
3. **Advertise only executable control actions.** The preferences task exposed a native `<select>` as a typeable combobox. Luna followed that advertised action, and Playwright rejected `fill("Express")` because the element was not an input, textarea or contenteditable element. Follow-up commit `dd64c63` removes that false `type` affordance, with a regression covering native select, editable input combobox and contenteditable textbox. It does not implement option selection; a real select-option capability remains needed. The model trial above predates this fix.
4. **Verify live UI updates as well as stored results.** In this run the visible application remained on old Running states and an empty Browser pane after native thread reads already contained completed results. Reloading the renderer restored all threads, completed status and the final page snapshot. The triggering setup included an initially hidden window and multiple external protocol clients. The exact missed-event or projection cause has not been isolated; a reload is evidence of recovery, not a product fix.
5. **Improve observation density.** The local WinApp screenshots contained the editor in the upper-left portion of a much larger black image. Chinese text remained legible, but the unused area wastes visual input. DPI/capture sizing needs a separate reproduction. Computer inspection also omits editable values, so Luna needed a screenshot plus image viewing to verify its input.

A separate manual Electron-provider diagnostic could toggle the preferences checkbox and verify its saved value, but did not expose the contenteditable note as an actionable target. Its checkbox target did not include structured checked state. Do not generalize these Electron observations to Playwright: the providers expose different target sets.

## Evidence and reuse

Use the [small-task suite](../evals/browser-computer/README.md) for prompts and grading. B6 adds a native select, checkbox and contenteditable preferences task; honest partial completion is `unsupported`, not `pass`. Persist action traces and a final observation, and inspect nested tool outcomes rather than counting an outer `run_code` exit code as task success.

Raw local traces contain desktop window titles and machine paths and are deliberately not committed. Credential files are never evaluation output. Earlier Codex and DeepSeek comparisons remain provider-level exploratory evidence in [the capability comparison](browser-computer.md); they are not matched model benchmark scores.
