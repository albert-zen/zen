# App Shot

Enable the shortcut for the current Composer, switch to an external application and press both physical Shift keys together. Its window is captured and added directly as a draft image; click that attachment to inspect its actual captured context. Sending is separate.

For manual window selection or shortcut setup, use the computer icon beside the Composer attachment button, or press Cmd/Ctrl+Shift+2 while the Composer has focus. Select a window, review the screenshot and captured context, then choose **Attach to draft**. Sending remains a separate action. Completed review captures are staged only in bounded process memory (four previews per renderer and 40 MiB across the Host, expiring after five minutes). Cancel or leave the Composer to discard them; the manual Attach action creates an owner-bound lease in the existing draft attachment staging store. Permanent attachment publication remains part of ordinary Send; cancelled late Attach results retire their draft lease.

On macOS selected-window captures and macOS/Windows foreground captures, the optional checkbox reads bounded accessibility context from the exact window. The context may contain a semantic tree (role, name, value, description, child hierarchy, sparse control states and advertised action names) or a flat-text fallback. These are descriptive data only, never action calls, selectors or control permissions. This can include text outside the screenshot. A failed or unavailable read is marked screenshot-only; the application is never clicked, activated or typed into by this capture path. macOS Screen Recording and, for context, Accessibility permission are controlled by the OS.

Global capture must be explicitly enabled for the current Composer. On macOS/Windows the default choice is **Both Shift**: simultaneously hold physical left and right Shift, not a double tap. The other fixed pairs are **Both Control**, **Both Option/Alt**, and **Both Command/Windows** (Meta). Each observes only its selected left/right physical state bits using T3’s 50ms polling and rising-edge latch, without recording typed keys or reserving the keys exclusively. A pair already held at enablement may trigger immediately. Windows keys may also open the system menu, and Alt may activate application menu bars; the corresponding choice shows this warning. Cmd/Ctrl+Shift+2 remains an alternative. Record a custom modifier-plus-key chord with the focused recording button; Escape cancels, Tab leaves recording, repeats are ignored, and element/window blur, page hiding or unmount stops recording. Recording follows T3’s layout-letter and physical Digit/punctuation handling. Selection performs only static validation and never temporarily registers or suppresses a global shortcut. Explicit Record obtains a transient, ownerless-only recording admission; an active shortcut in any Composer must first be disabled through its own UI, and no new shortcut can be enabled while recording is admitted. Matching cancel/finish, blur/unmount or renderer cleanup releases it. A failed release remains visible and blocks Enable until explicitly retried or the owning window closes. Only its exact-token unresolved cleanup receipt survives Composer replacement in transient renderer memory; a new Composer can show and explicitly retry that release, without restoring recording. Pending admission responses are fenced by their exact token. Common editing/system conflicts, ZenX Mod+1–9 navigation, macOS zoom, Windows/Linux Alt+F4 and Windows Ctrl+Shift+Escape conflicts and unsupported keys are rejected; availability in other apps is checked only by registration at explicit Enable. Choices cannot change while armed or busy. Main-process validation accepts only fixed pair enums or strictly validated modified chords before changing owner or registering. Native workers still never accept arbitrary virtual-key codes or masks. The owner unregisters its exact registered accelerator. The local Cmd/Ctrl+Shift+2 picker remains available when a different custom chord is armed. Switch to an external app and press the chosen shortcut; ZenX identifies and captures the foreground window before returning to ZenX and automatically adding an image-style attachment to the owning Composer. No capture modal or extra Attach click is required. Clicking that draft attachment opens its image and exact appShotContext; only ordinary Send submits it. Leaving or disabling that Composer cancels pending startup/work and releases the shortcut. Only explicit pair or validated chord selections are remembered locally for new Composers and app restarts. Each Composer takes its own initial snapshot; another Composer or a storage event never changes its live choice. Unknown stored values use the platform default, and Linux uses the chord even if any physical pair was saved, and rejects physical-pair requests without starting a worker. A failed save is shown while retaining the choice for this Composer. Enablement, application-text selection, owner tokens, portal authority, captures and drafts are never restored from this preference. Reading the preference never arms, captures or sends. Failures visibly disarm; there is no restart loop. On Niri 25.11+ the same Composer opt-in registers a Zen-namespaced session-bus action. The dialog shows a manual Ctrl+Shift+2 binding for the user's existing Niri binds block; registering the action does not reserve keys or edit configuration. Other Wayland sessions use the desktop GlobalShortcuts portal for an explicit consent-aware binding. Unassigned shortcuts remain visibly disabled; Configure is a separate user action and the actual desktop-assigned chord is shown. Closing/disabling the Composer closes its session, but the desktop may remember its user-granted choice. X11 retains the explicit chooser.

macOS selected and foreground captures follow T3’s exact CoreGraphics window-ID surface path: `/usr/sbin/screencapture -l <windowId> -o -x -t png`. Window enumeration always requests zero-sized thumbnails, including on capture; it never collects all-window thumbnails or substitutes a screen rectangle. Exact external PID, title and bounds are required before pixels. Foreground capture also preserves its initial observed identity through the selected-window path. Missing metadata, own-window exclusion, identity changes, denial or cancellation fail closed without another target. Capture omits the drop shadow and fits the image within 2560 × 1600 without upscaling.

The macOS native tool briefly writes a PNG into a unique mode-0700 temporary directory. After confirmed child close, ZenX bounded-reads a regular non-symlink, single-link file, validates the compressed byte and pixel budgets before native decode, and deletes the directory before successful memory-only review. Cancellation or the 15-second capture deadline kills only the owned child and waits for close. If shutdown cannot be confirmed within one additional second, the request fails and cleanup is deferred until that child's close; it cannot promise removal after an application crash or an unconfirmed child shutdown. A cleanup failure discards the capture and reports failure. This is transient native transport, not saved review or a recovery store. Fresh identity/exclusion checks surround pixels and optional text. Checks are observations, not an atomic OS pixel/metadata transaction. Neither the tool nor accessibility changes permissions, and there is no region/all-window fallback.

Windows follows T3’s Win32 identity → screen-to-DIP rectangle → isolated xa11y region capture path. These are visible desktop-region pixels, not an HWND surface: overlapping windows can appear. Target HWND/PID/title/bounds are checked around capture and optional text. The unchanged Windows explicit picker, and the supported X11 picker, use Electron's window thumbnail enumeration before filtering the chosen source; they do collect other windows' thumbnails at capture time and are not the macOS exact-surface path. Mac accessibility uses the same pinned xa11y worker path with PID/title/geometry checks. No capture path grants OS permissions or enables accessibility. Native packages are pinned to ffi-rs 1.3.2 and xa11y 0.13.0 and explicitly staged in portable packages.

## Shortcut delivery and attachment inspection

After explicit enablement, supported foreground shortcut captures go directly through the existing owner-bound draft staging API. The image remains outside the input like other draft images, with an App Shot label. Clicking it shows the actual stored appShotContext, including metadata, text availability and optional accessibility data; the view does not reconstruct or send context. Removal deletes its pending context too. Manual window selection remains an explicit fallback with its existing preview and Attach action.

A transient four-capture queue preserves event order through slow staging. Revocation, disable, unmount or API/Composer replacement invalidates its generation, discards queued previews and retires any late imported lease. An older unsettled import cannot drain or unlock a newer queue. Recent 64 capture IDs suppress duplicate events; the host's consumed-preview check remains final admission. Closing the settings/manual picker alone does not revoke a shortcut or its independent import. Failed imports and overflow are visible; no automatic retry, durable recovery, OS grant or Send is added.

This matches T3's direct draft delivery and on-demand attachment details, while retaining ZenX's local staging until Send. T3's source can upload draft attachments before Send; that behavior is not transplanted.

T3 uses direct active-window capture on macOS/Windows, a default both-Shift shortcut, optional accessibility trees/text, and Linux compositor helpers/picker support. Its `RegionSnapShot` class captures the Windows active-window bounds; it is not an interactive crop tool. T3 also persists its enabled setting and supports arbitrary modified chords. ZenX supports the same four fixed modifier pairs and supported modified chords, remembers only the selection, and deliberately keeps enablement explicit per Composer. Static selection validation does not transplant T3’s temporary registration/polling or global suppression authority. T3 may upload an attachment to a connected server before Send. ZenX keeps this feature's capture local until ordinary Send and uses its existing attachment transfer path.

This is a staged port toward T3 parity, not a claim of completion. Remaining gaps: managed, explicitly approved Linux helper/GNOME setup and configuration flows; Niri/Hyprland config proposal/save and configurable compositor bindings; native acceptance of conditional image-relative accessibility child bounds; pending-capture recovery; sound/flash feedback; and own-ZenX-window capture. Windows explicit picker captures remain screenshot-only; native text is available for foreground capture. No denied/cancelled backend silently falls back to full-desktop or another target. Linux helper installation, extension enabling, or compositor config changes must be separate explicit actions.

The adapted native source preserves the upstream MIT notices and algorithms rather than substituting PowerShell or synthetic keyboard input. A hosted CI pass cannot establish real desktop permission, multi-monitor DPI, RDP-disconnected, or Wayland compositor behavior.

## Niri transport and setup boundary

Niri capture preserves T3's subscription-before-command order, exact caller-owned output path, window ID, completion event and metadata recheck. Identity drift retains pixels but omits metadata. Known ZenX process IDs are excluded before capture; null PIDs remain unknown. No compositor failure silently falls back to another target.

The action exists only while explicitly enabled for the current Composer. Production and development use distinct Zen-owned bus/interface/path names. Same-session bus callers are not authenticated physical key presses. Disable or leaving the Composer unregisters the action. ZenX never reads or changes the user's compositor configuration in this stage. Manual binding removal is the user's action; disabling the action is separate.

Cancellation closes owned request/event sockets and discards output. It cannot retract a ScreenshotWindow request already accepted by Niri; a late compositor write may fail or recreate a private temporary file after cleanup.

The exact dbus-next 0.10.2 dependency is patched during workspace postinstall and portable staging using reviewed original/final Git-blob hashes. The patch is the same as T3's: Node net supports path and abstract session sockets, and optional usocket/Unix-FD passing is removed. Only the pinned 17-package pure-JS closure is staged, with upstream licenses. Clean npm-ci and packaged import validation are required; changing the dependency version fails closed.

## Generic Wayland portal

A read-only support query checks Screenshot version >= 3 and AvailableTargets bit 8 without taking pixels. Explicit capture pins the service owner, subscribes before requesting target 8, handles an early response, and closes unfinished Request objects on cancellation/deadline. Missing capability opens the explicit chooser. Denial, cancellation, malformed replies and transport failures do not fall back.

Generic portal captures are pixels-only: no guessed application/window identity, no accessibility correlation, and no verified exclusion of ZenX itself. The portal owns its result file; ZenX bounded-reads but never deletes that file. Capture and shortcut sessions have separate connection-scoped Registry identities; installed desktop-entry identity and actual compositor permissions still need native acceptance. Production uses `io.github.albert_zen.ZenX`, development adds `.Development`. No desktop entry is installed automatically. Portals that require an installed entry can reject portable launches until the user installs a matching launcher.

GlobalShortcuts consent is requested only when the user explicitly enables the current Composer, and ConfigureShortcuts v2 only on its explicit button. A rejected/unassigned binding is not armed. Disable and Composer changes close owned requests and sessions; no permission is automatically granted or restored. When this ZenX Composer is already focused, its portal trigger opens the explicit chooser instead of taking pixels, preserving the local picker shortcut without interpreting localized shortcut descriptions. The normalized selected chord is sent as preferred_trigger, with a stable action identity keyed to that preference. Unsupported keys fail before requesting consent. The desktop may assign another chord; its returned description remains authoritative. Niri and Hyprland expose separate action/config instructions, not the ordinary chord recorder. Hyprland still submits no preferred_trigger and offers no Configure button.

## GNOME extension and Linux accessibility

GNOME 45–51 Wayland hosts may use the bundled extension adapted from the same T3 revision. Full Linux packages ship the five runtime sources, MIT license, provenance and setup guide under `resources/app-shot-gnome`, outside app/ASAR. Shipping is inert: the user must review/install the extension, sign out/in and explicitly enable it. ZenX does not install/update it, enable global user extensions or change desktop permissions. The Composer shows read-only readiness and a collapsed setup/revocation explanation; Refresh windows also refreshes readiness. See the bundled [setup guide](../resources/app-shot-gnome/README.md).

A ready version-2 GNOME service is preferred before the generic portal. The client claims a fixed Zen-specific name on its dedicated connection, pins the extension owner and receives pixels with compositor metadata. Known ZenX PIDs are excluded; an unknown PID cannot prove self-exclusion. Capture checks cancellation, clean EOF, bounded PNG dimensions and a 15-second deadline. Synchronous native decode cannot be preempted, but late results are rejected. Extension denial/failure does not fall through to a different backend. Revoke persistent capture access by disabling the extension in GNOME Extensions; stopping the Composer shortcut only closes the shortcut session. The same-session bus-name allowlist is not executable authentication.

When optional text is requested, verified GNOME/Niri PID, title and logical dimensions enter the existing isolated xa11y worker. Wayland identity matching uses logical dimensions independently of position. Reliable GNOME/KDE/Hyprland origins already observed during capture remain private inputs for conditional image-relative mapping; no screen origin or control target is invented. Niri retains its supplied window ID; GNOME does not invent one. Missing identity and generic portal pixels never trigger an accessibility lookup. The reader bounds metadata scanning and text, permits unnamed GTK4 windows only within the known PID, and rejects ambiguous matches. A Flatpak proxy fallback examines bounded application/window metadata only when the PID lookup is genuinely missing or successfully empty; permission and transport errors never authorize that scan. Only the uniquely matched window tree is read.

Linux accessibility needs the platform AT-SPI runtime (for example Debian's `libatspi2.0-0t64` or `libatspi2.0-0`) and application support. ZenX does not install these or enable accessibility settings. A read failure/timeout remains screenshot-only. Fresh AX object validation is not an atomic pixel/text snapshot or current compositor proof. The pinned xa11y implementation can turn some native child-read failures into an empty result; that inherited limitation is not claimed away. The semantic tree uses the same uniquely matched window and identity revalidation; it does not expose selectors or grant control. Niri child bounds remain null because its zero origin is a placeholder, not a globally comparable compositor position. Generic portal pixels still never trigger an AX read.

## Accessibility semantic context

The pinned T3 reference serializes role, name, value, description, hierarchy, sparse states and advertised action names, with flat-text fallback. ZenX follows these descriptive fields in the existing isolated read-only worker, using one bounded traversal to derive both representations rather than T3's parallel full/flat reads. It never exports raw native metadata, PID, handles, object paths or action targets. Existing same-window matching and post-read identity validation remain required; failed revalidation, cancellation and timeout discard context rather than returning unchecked late snapshots.

Output is limited to 10,000 visited nodes, depth 64 and 32,000 serialized characters, with per-field limits and Unicode-safe trimming. The root uses the actual captured-image dimensions. Matched macOS/Windows child geometry is mapped from logical screen bounds to those pixels using rounded edges and image clipping; Windows rescales every non-null node after its pixel resize and validates the complete result again. Missing, unsafe, off-image or rounded-away child geometry stays null without dropping semantic text. On Wayland, coordinates require both trusted frame/client origin agreement with the observed AX root (within two logical units) and at least one valid descendant origin varying by more than two units from that actual root. Matching client dimensions take precedence, while the captured frame remains the mapping source when client metadata exists so title-bar offsets are preserved. A frame/client offset alone is not descendant variation. The existing post-read top-level AX identity check also downgrades all descendant coordinates when fresh root position is no longer reliable; identity failure still discards all context. No extra enumeration or compositor query is added. Missing dimensions permit flat text only, not invented image coordinates. These are output/JavaScript traversal budgets, **not hard limits on each native provider read**: xa11y can materialize a full string or a child collection before JavaScript receives it. The outer disposable-worker deadline remains the isolation boundary. Large or deep trees are truncated explicitly; flat text is preferred when rich serialization would discard text it can preserve.

Descriptions and values can include information outside visible screenshot pixels. The pinned T3 serializer does not itself remove protected/password fields, and xa11y does not expose reliable cross-platform protected-field metadata. Known macOS/Linux secure-role subtrees are conservatively omitted before serialization, without exporting the internal raw role metadata; this does not establish a Windows or universal protected-field guarantee. Do not treat optional accessibility context as automatically redacted or safe to send without review. The existing text checkbox stays opt-in, captured data is inspectable from the draft attachment, and ordinary Send remains separate; no capture or advertised action name can send or control another app.

## KDE and Hyprland native capture

On Wayland, a ready user-managed KDE or Hyprland helper is selected before the generic portal. Ordinary X11 native capture remains unavailable, matching T3's outer desktop gate. KDE uses the dedicated ScreenShot2 executable plus its separately installed desktop authorization entry; Hyprland uses full-width window mapping and export-v2 protocols. Both retain T3's capture algorithms, bounded private PNG transport and pre/post identity checks. Hyprland explicitly checks lock state before and after export. Like pinned T3, KDE has no independent helper lock query and relies on the compositor. KWin v6.4.3 suppresses its screenshot effect once its watcher observes Locked; its GetActive state does not cover AcquiringLock. This is a source-derived residual race, not a reproduced capture leak or evidence that ordinary explicit capture is unsafe. There is no measured occurrence rate. A capture already requested by the user could overlap an automatic or separate lock transition; any accepted result still enters only the local draft, never automatic Send. KDE remains available under these upstream-equivalent boundaries, without claiming an atomic lock-transition barrier or native lock-race acceptance. No helper is installed, updated, authorized or added to compositor configuration automatically.

The read-only Composer state distinguishes ready, absent setup, incompatible helper and error. Missing capability may select an available generic portal, but denied/failed native capture never does. Hyprland installed-but-unusable/version-error state is fail-closed rather than treated as absence. Capture identity may be omitted after metadata drift or unavailable KDE scripting; image-only results cannot establish self-exclusion or identify accessibility text. With a verified positive PID/title, observed frame/client logical geometry feeds the existing bounded AT-SPI worker privately, never fabricated Wayland origins or coerced KDE UUID window IDs.

Hyprland uses the GlobalShortcuts portal's fixed `capture-window` action without `preferred_trigger`. The action registration is separately represented from physical key registration: the UI never claims keys have been assigned. User-managed legacy or Lua bindings target the production `io.github.albert_zen.ZenX:capture-window` action (development adds `.Development`). The portal's verified activation events may trigger capture only while the current Composer owns the session. There is no Configure button, no Niri bus-action fallback and no config write. Disable closes that session; removing the manual binding or helper remains the user's action.

Full Linux x64 packages stage inert distributions under `resources/app-shot-linux/{kde,hyprland}` outside app/ASAR. Source builds require the pinned lockfiles, tests and complete dependency notices. The package builder accepts a reviewed CI distribution via `ZENX_APP_SHOT_LINUX_DIST`, validates ELF/architecture and glibc <= 2.35, and does not claim arm64 native-helper support. Existing Linux arm64 app packaging remains available: the automatic native-helper stage skips before I/O/build while GNOME/Niri/portal stay available; an explicitly supplied unsupported native artifact is rejected. Native build/transport tests run separately on Ubuntu 22.04; they exercise synthetic protocol peers, not a live compositor or its permission UI. See [distribution notes](../native/LINUX-DISTRIBUTION.md), [KDE manual setup](../native/kde-snap-shot/README.md) and [Hyprland manual setup](../native/hyprland-app-shot/README.md).

## Verification

Focused checks: `node --import tsx --test apps/zenx/test/app-shot*.test.ts`.

The macOS surface tests use synthetic files, fake child processes and injected image decoding. They cover exact fixed command arguments, zero-thumbnail service routing, required identity and foreground/selected expected-identity narrowing, cancellation, deadline/close ordering, late output, failed cleanup, byte/dimension limits and no alternate target. These tests do not execute screencapture, grant Screen Recording, inspect another app or establish native occlusion/scale behavior. The host-only optional expected identity is a narrowing assertion for a known target; renderer IPC does not accept it.

Offline actual-component preview: `node apps/zenx/scripts/build-app-shot-preview.mjs /tmp/zen-app-shot-preview`, then open its `app-shot.html` (add `?mode=preview` for the captured state and `&theme=dark` for dark mode). All content and images in this fixture are synthetic. It does not use the capture backend or inspect real applications.

The `App Shot synthetic UI and native bridge` workflow combines focused contracts, production-component synthetic screenshots, and bounded native bridge probes:

- Ubuntu Chromium captures the real component in light/dark and desktop/narrow layouts, with authenticated CJK fonts. It checks picker, review, expanded image, cancel, reopen, explicit Attach without Send and Escape, plus custom-chord recording and Escape cancellation without capture/arming, hidden recorders on Niri/Hyprland, all four fixed pair labels, Windows menu warnings and an explicitly selected Meta pair surviving a fresh page with capture and text still disabled. PNGs, source SHA, geometry and browser lifecycle receipts are retained. Run after the builder with `node apps/zenx/scripts/capture-app-shot-preview.mjs /tmp/zen-app-shot-preview` in GitHub Actions. The existing preview helper uses a disposable profile and disables its browser sandbox; this is synthetic CI evidence, not a user browser.
- macOS executes the exported production JXA directly using `/usr/bin/osascript`, within the production two-second command budget. The null-window test requires the script's own expected refusal, so an invalid ObjC/CoreGraphics bridge fails instead of hiding behind the wrapper's generic error. Foreground metadata is checked only when the runner provides an exact title; missing foreground/title or a retired window is recorded as blocked. No arbitrary runner titles or PIDs are retained. Run with `ZENX_APP_SHOT_JXA_SMOKE=1 ZENX_APP_SHOT_JXA_EVIDENCE=/tmp/app-shot-jxa.json node --import tsx --test apps/zenx/test/app-shot-native-smoke.test.ts` on the macOS Actions runner.

Native smoke checks sample all four fixed modifier pairs finitely and start/stop the modifier workers without injecting keys and read bounded Windows FFI/macOS JXA metadata. They never grant/reset Screen Recording, Accessibility or Input Monitoring permission. Passing metadata or worker lifecycle checks does not establish screenshot pixels, AX text, physical shortcut activation or full desktop acceptance. The native smoke does not create a controlled external window, so its positive metadata result is only an observation of the disposable runner; release acceptance still needs the controlled-window checks below. Embed reviewed Chromium screenshots from the matching commit in the PR before merge and label their synthetic data boundary.

Before release, perform native macOS/Windows acceptance with a disposable external window: deny permission, grant permission, capture with and without text, switch foreground during capture, close/rename the selected window, change Composer while capture is pending, repeat the shortcut, cancel review, attach and remove, then send to a test provider and inspect the admitted input. Repeat the picker on each supported Windows/Linux desktop. These native checks cannot be established by injected tests on a Linux build host.

Coordinate unit tests establish source-derived mapping, clipping, reliability gates and resize behavior only. Native acceptance remains required for macOS final PNG scale/decorations, Windows mixed-DPI monitor seams and occlusion, and actual GNOME/KDE/Hyprland AT-SPI origins, decorations, fractional scaling and move/resize races. xa11y 0.13.0 documents limitations for Windows windows crossing differently scaled monitors; image coordinates are descriptive and never input targets.

## Owned macOS native acceptance

Same-repository pull requests in `.github/workflows/app-shot.yml` execute
`scripts/verify-app-shot-macos.mjs` only on a hosted macOS runner, so the exact
draft can be checked before merging the workflow into the default branch.
Fork pull requests cannot run this job. Manual runs retain the explicit
`macos_owned_acceptance` opt-in input; unrelated events do not enable it.
Review and build the exact production capture backend on the same commit first.
The harness refuses the old all-window-thumbnail adapter before capture. It uses
an isolated Electron package/userData, the real service, emitted worker/chunks and
`stageAppShotRuntime`; it never starts normal ZenX or reads its settings.

A directly spawned opaque AppKit fixture has a fresh 128-bit nonce in its title,
visible/accessibility label and known colored blocks. Its child PID, executable,
bundle, window ID, title and bounds must agree with fresh observations. Only
production exact-window capture is allowed. The selected and foreground calls
carry the original host-only expected identity; no screen-region fallback, input,
physical shortcut injection or foreground-acquisition loop is used. After fresh
ownership and permission checks, the launcher-owned fixture can receive one
nonce-bound request through its private scratch directory to activate itself.
The request is consumed before activation and never retried, including after an
uncertain write. Only bounded foreground/identity observation and private nonce
probe writes follow, with no further activation or input. The fixture's own
active flag and the real production foreground PID/window identity must both
agree before capture; failure remains blocked. This test-only setup never
activates another application and does not change production capture behavior.

The exact Electron main process must already report Screen Recording `granted`;
AX additionally requires `isTrustedAccessibilityClient(false)`. The harness never
requests permissions, modifies TCC, opens Settings or grants anything. Returned
PNGs are decoded and checked for dimensions and the full nonce pattern. AX must
return a descendant label with that nonce and matching captured-image dimensions
and bounds. The fixture stops only through its private stop file, with actual
owned-child close required before successful cleanup.

Exit 0 requires pixels, AX, foreground and cleanup all passed. Exit 2 means a
permission/session/identity prerequisite blocked acceptance, not a passing or
skipped native test. Crashes, timeouts, bad markers and unconfirmed cleanup exit 1.
The always-upload artifact allowlist contains only `receipt.json` and verified
synthetic `selected.png`, `accessibility.png`, `foreground.png`. It excludes raw
AX payloads, arbitrary titles, native stderr, runner inventory and private scratch.
The local fake-contract tests are not native capture evidence. Strict owned-only
Windows capture remains blocked because its current backend captures a visible
screen region that may contain overlapping surfaces; this harness has no Windows
capture branch.
