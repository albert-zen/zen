## What this inspection does not establish

Across the published main tree and relevant 0.146.0 source, searches for native event injection, accessibility targeting, occlusion, and Playwright/CDP execution did not identify an implementation of desktop click/type/drag, target focus recovery, window-overlap rejection, or browser automation execution. Playwright references found were approval-test examples; a ScreenCaptureKit framework declaration is not a driver.

Consequently, the source cannot establish how the shipped Codex desktop backend treats a mouse-ignoring Dock overlay, a covered application window, or an arbitrary DOM evaluation request. Absence from this inspected tree is a coverage limit, not proof that the shipped product lacks those capabilities.

## Implications for Zen #593

- **Do not equate geometric overlap with interception.** A frontmost Core Graphics rectangle alone does not establish that the corresponding surface receives the input. The inspected Codex source does not require Zen's conservative “any overlapping rectangle means reject” rule. A mouse-ignoring overlay false positive should be addressed using verified macOS behavior and adapter tests.
- **The native accessibility/hit-test fix is Zen's adapter choice.** It is not copied from, or evidence about, a proprietary Codex backend. Any permission-unavailable fallback and uncertain-target outcome should remain explicit rather than silently guessing the input recipient.
- **Preserve existing consent and stop semantics.** Within already authorized scope, ordinary programmatic operations should not acquire new repeated confirmations merely because they are clicks, typing, or drags. Genuine permission changes, consequential actions and applicable approval requirements remain distinct from recoverable focus/targeting conditions. Cancellation must prevent subsequent dispatch.
- **Separate command acceptance from delivered effect.** Dispatch, denial, cancellation, timeout and uncertain outcome must remain distinguishable. A successful native API return or passing unit test is not proof that the intended application received the click or text. Delivered effects—including target identity, focus and observed UI changes—must be checked separately in appropriate native acceptance tests.

The alignment goal is a usable programmatic operation surface with accurate authorization and outcome reporting—not blanket refusal, blanket permission, or an unsupported claim of exact native-backend parity.
