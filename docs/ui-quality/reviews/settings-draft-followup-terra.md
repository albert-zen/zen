## Remaining findings

1. **P2: stale activation read can overwrite a newer provider result.** `SettingsView.tsx:167–190` does not guard the asynchronous `settings.get()` result by revision. Reopen Settings with a pristine draft while a provider save is pending, let the read start, allow the provider response at revision 2 to finish first, and finally resolve the read with revision 1. The read unconditionally replaces `settings` with revision 1 while its identity guard preserves the newer draft. Provider display and the base revision used to open a provider editor can regress, yielding stale content or revision conflicts. Regression: defer the activation read, return the newer provider response first, then the older read, and check provider list and revision remain current. Guard activation reads against already-observed newer authority as well as provider callbacks.

2. **P2: a delayed activation read can misclassify untouched fields as edits.** `SettingsView.tsx:173–190, 1328–1348`: when a read begins with a pristine draft, the user can edit one field before it returns. The read then installs the newer Host profile as `settings` but preserves the entire old draft because object identity changed. In a subsequent provider response, the rebase compares that old draft to the newer Host baseline, incorrectly treating independently changed Host fields as local edits. For example, while the user only edits queue mode, a read changes Host max from 4 to 8; a later provider response can keep old max 4 and an Apply can overwrite 8. Regression: defer the read, edit queue, return a newer Host maximum, complete a provider mutation, and check that max 8 and the local queue edit coexist. Rebase the delayed read using its captured start baseline and the latest draft, while preserving current authority and validating model references.

Both remaining findings were reported immediately to the lead and implementation worker. Full suite and native evidence are owned by the implementation worker and were pending at review time.
